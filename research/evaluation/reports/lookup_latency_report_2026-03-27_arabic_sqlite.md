# Arabic SQLite Lookup Latency Report

Date: 2026-03-27

Input: the Arabic paragraph beginning with `vالزُّكام...`

Scope:
- `POST /api/lookup_batch`
- `GET /lookup_dp_only`
- SQLite segmenter path in `sqlite_segmenter.py`
- Universal normalization wrapper in `universal_normalization.py`

## Bottom Line

The SQLite batch lookup path is not the bottleneck.

The slowdown is in the paragraph-length SQLite segmenter path, specifically:
- span enumeration and normalization in `_build_span_key_matrix()`
- candidate fan-out in `_prefetch_candidate_keys()`
- SQLite key lookup fan-out in `lookup_candidate_rows_for_normalized_keys()`

Universal normalization is not the issue. It is under 1 ms on warm runs for this text.

What explodes is the single-token segmenter path when the paragraph is treated as one lookup unit. That path is O(n^2) in substring count before it ever reaches SQLite.

## Direct Measurements

### 1. Batch lookup

Probe:
- `POST /api/lookup_batch`
- `lang=ar`
- `tokens = paragraph split on whitespace`

Result:
- `314` tokens
- `entry_count = 0`
- `query_ms = 4.6 ms`
- wall time: `47.33 ms`

Interpretation:
- This is fast.
- It does not exercise the expensive paragraph-length segmentation path.
- It is not where the timeout is coming from.

### 2. Universal normalization wrapper

Probe:
- `run_with_universal_normalization(...)`

Result:
- warm runs were about `0.75-0.80 ms`
- `build_preprocess_context(...)` was about `0.74-0.83 ms`

Interpretation:
- Arabic normalization in the wrapper is not the bottleneck.
- The wrapper is cheap compared with the SQLite segmenter path.

### 3. Per-token segmenter on whitespace tokens

Probe:
- `SQLiteDictionarySegmenter.fill_token(token)` for each whitespace token in the paragraph

Result:
- `314` tokens
- total time: `12.04 ms`
- average per token: `0.0379 ms`
- median per token: `0.0204 ms`
- `_normalize_key` cache:
  - `96` misses
  - `6740` hits

Interpretation:
- Small individual token lookups are cheap.
- The explosion is not in a normal short-token lookup.
- The problem appears when the paragraph is forced through the paragraph-length segmenter path.

### 4. Full paragraph single-token segmenter path

Probe:
- `GET /lookup_dp_only?lang=ar&q=<full paragraph>`

Result:
- did not complete within the 120 second client timeout

Interpretation:
- This confirms the segmenter path blows up on paragraph-length Arabic input.
- The timeout is inside the SQLite segmentation flow, not the batch API.

## Call Chain

The expensive path is:

1. `/lookup_dp_only`
2. `_build_lookup_dp_only_payload()`
3. `_build_results_by_seg()`
4. `_build_segment_result()`
5. `SQLiteDictionarySegmenter.build_surface_lemma_aware_lookup()`
6. `SQLiteDictionarySegmenter.lookup_all()`
7. `SQLiteDictionarySegmenter.fill_token()`
8. `SQLiteDictionarySegmenter._greedy_fill_simple()`
9. `SQLiteDictionarySegmenter._build_span_key_matrix()`
10. `SQLiteDictionarySegmenter._prefetch_candidate_keys()`
11. `lookup_candidate_rows_for_normalized_keys()`
12. `dict_lookup_sqlite._query_candidate_db_grouped()` and `dict_lookup_sqlite._query_custom_candidate_entries_grouped()`
13. repeated `dict_lookup_sqlite._normalize_key()` calls for span strings, candidate keys, and match checks

The first exact lookup is cheap.
The cost appears when exact lookup misses and the greedy span path activates.

## Estimated Latency Split

These percentages are a best estimate from the current probes plus the earlier instrumented trace.

| Stage | Estimated Share |
| --- | ---: |
| `_build_span_key_matrix()` plus repeated `_normalize_key()` over every substring | 65% |
| `_prefetch_candidate_keys()` plus SQLite `IN` fan-out | 22% |
| `lookup_candidate_rows_for_normalized_keys()` plus DB grouping / dedupe | 8% |
| Outer route glue, JSON shaping, misc lookup bookkeeping | 5% |

## Why Arabic Hurts More

The Arabic path is expensive because several costs multiply:

- `_normalize_key()` does NFKC, invisible-character stripping, Arabic mark stripping, Arabic letter folding, and final cleanup.
- That normalization is run on every substring generated by the DP span matrix, not once per token.
- Arabic words in the paragraph contain diacritics, tatweel, punctuation, and non-spacing marks, so the normalization work is not trivial.
- The forms index is large, so the candidate key fan-out is broad once the span matrix starts producing keys.

This is not a bug in the sense of "wrong output".
It is an algorithmic placement problem: normalization is happening in the hottest possible loop.

## What To Fix

Priority order:

1. Normalize once per token, not once per substring.
2. Build the span key matrix from a pre-normalized token buffer and reuse the result.
3. Cache span matrices per input token within a request.
4. Put a length heuristic on Arabic greedy decomposition so paragraph-length tokens do not run full O(n^2) span enumeration.
5. Reduce candidate fan-out before hitting SQLite, especially for spans that cannot plausibly match Arabic forms.
6. Split Arabic normalization into a fast path for already-clean text.
7. Consider a trie or other in-memory segmentation index instead of querying SQLite for every unique candidate key.

## Practical Recommendation

Do not try to "optimize SQLite" first.

The DB queries are downstream of the real bottleneck.
The real fix is to stop normalizing and querying every contiguous substring of a long Arabic token.
