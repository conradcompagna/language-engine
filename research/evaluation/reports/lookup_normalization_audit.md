# Lookup Normalization Audit

Scope: this report covers only normalization that can change which dictionary entry is matched to which segment in the active hybrid lookup flow. I excluded UI-only formatting and generic text cleanup that does not participate in matching.

## Active Lookup Sources

`static/dictionary_normalization_layer.js` is the canonical key normalizer for the current system. `normalizeLookupKeyText()` is the real lookup definition: it applies NFKC, Ancient Greek apostrophe expansion, affix-marker folding, the registered rule pipeline, hyphen stripping, and lowercase normalization. The rule pipeline is where the language-specific lookup behavior lives. It currently covers invisible format controls, Ancient Greek breathings/accents plus final sigma folding, Modern Greek tonos and sigma folding, CJK variation selector stripping, Arabic-script mark stripping, Arabic and Persian letter folding, Urdu join-control stripping plus letter folding, Hebrew cantillation and niqqud stripping, Indic zero-width control stripping, Turkish case-prep, and Thai ZWSP stripping. The important bit is that this is not just "cleanup": the exact order of these rules decides which code points survive into the final key, so the client probe and the SQLite index have to normalize the same way or matches will silently fail. This is the shared lookup semantics for both browser-side matching and key generation.

`tools/normalize_keys.js` is not a separate rule set. It is the Node wrapper that loads `static/dictionary_normalization_layer.js` so Python can generate the same lookup keys when building SQLite indexes and custom-entry form indexes. If the shared JS rules change, this shim must stay aligned or the stored keys and runtime keys will diverge.

`dict_lookup_sqlite.py` is the active server-side bridge between normalized keys and the SQLite dictionary tables. The stale comment around `_normalize_key()` says "defunct", but the code is still live through `normkey` and `normkey_lang`, which are registered as SQL functions and used in lookup queries. The same file also uses `_normalize_keys_via_js()` when normalizing custom-entry forms, so the database layer is not just consuming precomputed keys; it still enforces the current lookup key space. In practice, this file is where the shared normalization becomes a queryable SQLite match. It is also where form keys and headword keys stay aligned with the JS rule set, which matters because a form can match even when the raw headword does not.

`static/dictionary_client_hybrid.js` is the active client-side matcher for segment-to-entry lookup. `normalizeLookupKey()` is the first client-side gate: it NFKC-normalizes, then delegates to the shared normalization layer, and only falls back to a lowercased key if needed. `chooseEntry()` uses that key to decide whether a candidate entry matches the current surface text. `normalizeVisibleComparisonText()` also affects lookup decisions, not just rendering, because the matcher uses it when comparing candidate surface and lemma-like strings that should be treated as equivalent. This file also carries lookup-relevant Korean-specific filters and comparison helpers, so it is one of the real matching layers, not a cosmetic layer. In other words, this is where a normalized key becomes an actual segment choice in the browser, which is the final decision point before hydration and rendering.

`static/dictionary_engine_hybrid.js` is the in-memory engine that drives dynamic-programming segmentation and candidate selection. Its lookup-facing normalization starts with `normalizeAffixMarkers()`, `normalizeLookupBaseProbeText()`, and `normalizeLookupProbeText()`. Those functions make the surface probe comparable before the DP matcher scores spans against indexed entries. The engine also normalizes Korean and Vietnamese XPOS tags, preferred POS lists, and Korean jamo comparison forms. These rules matter because they change which candidate entries are eligible for a span, which is exactly the matching problem. This is also the layer that deals with "same-looking" strings that are not byte-equal, so it is not just a filter on the output set. It is part of the decision tree that determines whether a span is considered an exact hit, a partial hit, or a non-match.

`universal_normalization.py` is upstream of matching rather than part of the dictionary key space, but it still affects lookup because it changes the text and offsets that reach Trankit and, therefore, the segments the lookup engine sees. The active pieces are NFKC normalization, stripping non-BMP characters, Arabic diacritic stripping in model space, and offset remapping back to the original text. I would treat this as lookup-input normalization, not dictionary-key normalization, but it still participates in the effective lookup path. If you change this file, you are changing what the segmentation step sees before the matcher ever runs.

## Dead Lookup Sources

`sqlite_segmenter.py` is dead server-side segmentation code. It still contains `_normalize_cached()` and `_normalize_visible_comparison_text()`, but none of that is on the current active lookup chain. It belongs to the old Phase 3 matcher and should be treated as archival.

`static/dictionary_postprocessor.js`, `static/dictionary_client.js`, and `static/dictionary_engine.js` are dead Phase 2 lookup stacks. They still contain the old `normalizeLookupKey`, `normalizeVisibleComparisonText`, `normalizeXposTag`, and `normalizeDedupKey` paths, but the hybrid reader no longer loads them. Any rule change in those files would not affect the current matcher.

`wiktionary_general/pipeline.py` and `wiktionary_general/dictionary.py` are dead pre-hybrid normalization code. They still NFKC-normalize, casefold, and perform lookup-text and affix-marker handling, but they are not in the active segmentation-to-entry matching path. Those functions are useful only as historical context for why the current JS rule set looks the way it does.

I am intentionally not counting `static/reader.js`, `static/reader_wikt.js`, `router.py` display helpers, or `pipeline_common.py` UI/payload helpers here. They may normalize data, but they do not decide whether a dictionary entry matches a segment during lookup. That boundary keeps this report limited to the actual matching logic.

## Bottom Line

If you change lookup semantics, the files that must stay in sync are `static/dictionary_normalization_layer.js`, `tools/normalize_keys.js`, `dict_lookup_sqlite.py`, `static/dictionary_client_hybrid.js`, and `static/dictionary_engine_hybrid.js`. If the change also affects the text before segmentation, include `universal_normalization.py` as the upstream input normalizer. Everything else is either dead lookup code or non-matching presentation logic.
